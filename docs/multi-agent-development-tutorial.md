# 从第一个 Tool 到一份可复核的仓网建议

## 先从要解决的问题开始

你刚加入一个电商履约团队。运营负责人提出了一个看起来很简单的问题：

> 华东区希望把一日达覆盖率提高到 90%。我们是否应该在杭州增加一个仓？

一份能用于决策的回答不能只有“建议开仓”。它至少要说清楚：

- 当前覆盖率是多少，分子和分母分别是什么；
- 不增加仓、只调整分配关系时能做到多少；
- 增加杭州仓后覆盖率和成本怎样变化；
- 结论使用了哪一版需求、仓库、费率和路线；
- 哪些数据缺失、假设和成本项可能改变结论。

这就是整套教程要完成的成果。Agent、Thread、MCP、Skill、Supervisor 等词会在
解决问题的过程中逐个出现；第一次遇到时再解释，不需要提前背概念。

现在只需要知道一个最朴素的定义：**Agent 是能围绕目标选择下一步、使用工具并根据
结果继续工作的智能执行者**。至于它怎样保存上下文、怎样连接工具、何时需要协作，
后面的步骤会在实际用到时说明。

## 这套教程适合谁

教程面向第一次开发 Agent 的工程师。你只需要能阅读基础 Python、JSON，并会在
终端运行命令。完成后，你应该能把一个业务问题拆成：

1. 模型需要判断的步骤；
2. 普通代码必须稳定计算的步骤；
3. 需要从外部取得的数据或能力；
4. 多项职责之间可检查的交接物；
5. 失败时应停止并报告的条件。

教程使用仓库中的小型脱敏数据。所有关键数字都能人工核对，不需要连接生产数据库，
也不需要地图服务密钥。

## 学习路线

请按顺序完成三篇，不要从术语最多的第三篇开始。

| 阶段 | 先解决什么 | 完成后再认识什么 |
| --- | --- | --- |
| [第一篇：从 Python 函数到 Agent Tool](tutorials/hello-agent-quickstart.md) | 划分 Agent 与代码的职责，运行、理解并修改一项能力 | Agent、Task / Thread、Tool、MCP、Skill |
| [第二篇：第一次拆分职责](tutorials/hello-agent-team.md) | 分开“准备可信数据”和“计算仓网方案” | Supervisor、子 Thread、交接合同 |
| [第三篇：完成仓网规划](tutorials/supply-chain-agent-tutorial.md) | 回答是否增加杭州仓，并写出证据和限制 | Resource、输入快照、Artifact |

第一篇的问候示例只是最小的 Python Tool 练习，相当于编程语言的 `Hello, world`。
它不会被包装成真实业务。你会用它走完一次“改业务规则、改 Tool 接口、改 Skill、
重新验证”的开发循环。从第二篇开始，所有分工都来自仓网决策本身。

## 这里说的“开发 Agent”到底是开发什么

在本项目中，你通常不会创建一个名为 `Agent` 的 Python 类，也不是重新训练模型。
你是在设计一个 Agent 怎样完成目标：

| 问题 | 对应的开发内容 |
| --- | --- |
| Agent 要对什么结果负责 | 任务目标、输入、输出和停止条件 |
| 哪些事实不能让模型猜 | 普通业务代码和 Tool |
| 什么时候调用、先后顺序是什么 | Skill |
| Tool 怎样被 Codex 发现和调用 | MCP Server 与 Plugin |
| 哪些职责需要独立上下文 | 子任务 / 子 Thread 与 Supervisor |
| 怎样证明结果可信 | 业务数字、调用轨迹、失败行为和测试 |

因此，教程不会把“写一个提示词”“增加一个 Python 文件”或“启动两个 MCP Server”
直接称为多 Agent 开发。

## 第一站：让 Codex 调用一段确定性代码

open-web-codex 界面把每项持续工作称为 **Task（任务）**，底层对应 Codex
**Thread**。你可以先把它理解成：

> 一名 Agent 处理一项工作的上下文、消息和操作记录。

第一篇会让这个任务中的 Agent 调用 `hello.say_hello`。问候内容并不重要，
重要的是能观察到完整链路：

```text
用户提出目标
  → Agent 选择工作方法
  → 调用 Tool
  → 普通 Python 校验并计算
  → Agent 根据 Tool 结果回答
```

完成这一篇后，你会知道为什么“模型碰巧答对”不等于“能力已经接通”。

## 第二站：从一个问题中拆出两项职责

仓网决策中有两项性质不同的工作：

- **数据准备**：读取订单，汇总需求，检查缺失和促销影响；
- **网络规划**：在固定数据、路线、容量和服务承诺下计算覆盖率与成本。

两项工作分开，不是为了展示“多 Agent”，而是因为错误的责任不同：

- 数据汇总错了，应回到数据来源和口径；
- 规划计算错了，应回到路线、容量、成本或算法；
- 规划者不能悄悄改需求来得到更好结果；
- 同一版数据应该能支持多个候选方案。

第二篇先在一个 Thread 中按顺序跑通这两项职责。这样可以先验证业务链，再讨论是否
值得创建两个独立 Agent。你会在需要协调它们时认识 **Supervisor**：负责理解总目标、
委派子任务、检查交接物并汇总答案的上层 Agent。

## 第三站：交付一份真正能复核的建议

第三篇使用 100 个规划需求单位、两个现有仓和两个候选仓，依次回答：

1. 历史订单透露了什么，数据可靠吗；
2. 当前分配关系下的一日达覆盖率是多少；
3. 不开新仓、只重新分配时能做到多少；
4. 增加杭州仓后覆盖率变化多少；
5. 要达到 90%，最少需要新增几个候选仓。

最终输出不是一串 Tool 调用，而是一份决策摘要：

```text
建议
依据
口径
方案对比
数据质量
假设与未计入成本
下一步验证
```

## 动手前的最小准备

先确认仓库根目录是：

```text
open-web-codex/
```

第一篇会单独准备 `hello-agent` 的隔离环境；第二、三篇会准备仓网规划环境。需要在
浏览器中验证真实 Agent 调用时，按[本地运行手册](mvp-runbook.md)启动真实 Codex
模式。Fake Runtime 适合验证 Web 界面，不用于判断真实 Skill 或 MCP Tool 是否被调用。

## 如何判断自己真的学会了

每一步都用三类证据验收：

| 证据 | 回答的问题 |
| --- | --- |
| 业务数字 | 结果能否由 fixture 和公式人工核对 |
| 调用轨迹 | Agent 是否真的调用了指定 Tool，而不是自己编答案 |
| 失败行为 | 数据、Tool 或交接物无效时，是否停止并说明原因 |

只看到一段流畅回答不算完成。一个可信 Agent 必须既能成功，也能明确失败。

## 这套教程会实际做到哪里

你会真实运行 Python、Skill、stdio MCP Tool 和单任务仓网链路。Supervisor 和两个
专业 Agent 的职责会设计清楚，但当前练习不要求在 Web 中创建两个子任务；教程也不会
把两个 Skill 或两个 MCP Server 冒充成两个 Agent。
